# CJ-UI 文档检索优化 · 验证报告

> 本文回答一个问题：**我们改了 MCP 文档检索，怎么证明改得有效？**
> 写法约定：术语第一次出现时都会解释；每个数字都注明它是从哪测出来的。
> 配套文件：`PYRAMID_RETRIEVAL_SPEC.md`（改动方案设计）、`eval/`（测试题库与全部原始数据）。

## 术语表（先读这个，后文不再重复解释）

| 术语 | 含义 |
|---|---|
| MCP 检索服务 | docs-mcp-server。agent 写代码时用它按关键词查文档，相当于"帮 agent 查 API 手册"的工具 |
| 金字塔文档 | 我们自己编写的 CJ-UI 文档库，分三层：L1 总索引（1 篇）、L2 按场景的案例教程（10 篇）、L3 单个 API 明细（254 篇） |
| 召回率 | 衡量"查得准不准"：发 100 条查询，有多少条把正确文档带回来了。下文"真实查询召回"指只用手工写的、贴近实际用法的查询来算（自动生成的查询偏简单，分数会虚高） |
| 返回量 | 衡量"查得贵不贵"：一次查询返回多少字符。返回越多，占 agent 上下文越多、消耗 token 越多 |
| 运行日志 | 每次任务的完整运行记录（`bench-run/opencode.stdout.jsonl`），记录 agent 每一步调了什么工具、发了什么查询、返回了什么内容 |
| 对照实验 | 每次只改一个变量、其余不动，对比两组结果——用来确定每个改动各自的贡献 |
| 四个实验组 | 金字塔组＝只加载金字塔文档（不用 MCP）；原版 MCP 组；纯官方 MCP 组（原版 MCP，只索引官方文档）；**优化组＝本文的改进版 MCP**。其他报告里的"臂1/臂2/臂2b/优化臂"即依次对应这四组 |
| judge 评分 | 自动评分器（Qwen3.7-Plus 模型）对任务完成度打分，满分 100 |
| 单次运行 | 每个任务每个配置只跑一遍，没有重复多次取平均。同一任务重跑的分数波动可达 ±28%，所以端到端的小差距不可靠 |
| token | 模型的计费和上下文单位。一个任务的 token 总消耗 ≈ 对话轮数 × 每轮上下文大小，其中约 92% 是反复读取已累积的上下文（缓存读） |

## 0. 先说结论

| 在哪个层面验证 | 结论 | 关键数字 | 可信度 |
|---|---|---|---|
| 检索工具本身（离线出题测试） | 两项改动各自有效：文档拆分治好"查不到"，摘要卡片治好"一次拖回太多" | 真实查询召回 28.1%→81.3%；单次返回量 6758→672 字符 | 高（114 道题、变量隔离） |
| agent 实际使用（线上日志） | agent 正常用新工具，返回量可控 | 单次返回量中位数 14200→3404 字符（-76%），最坏从 34800 压到 4784 | 中 |
| 任务端到端（bench 全流程） | **检索不是 token 总消耗的主要来源，优化检索省不动总账** | 评分 83.9（原版 84.4，及格线 82.4）；token 降 30%/50% 的目标未达成 | 低（单次运行），且是否定性的 |

最重要的一条：**检索返回量只占任务总 token 消耗的约 0.26%**。想降总消耗，控制"来回修改多少轮"（执行规则）比优化检索有效得多。这是本次验证同样重要的产出。

## 1. 验证思路（六步）

1. **看日志**：agent 实际怎么查文档——用什么语言、查多少次、每次返回多大；
2. **找问题**：原版 MCP 差在哪；
3. **做改动**：两项改动，一项治"查不到"，一项治"返回太多"；
4. **出题**：构造 114 道检索测试题，每题有标准答案；
5. **做对照**：五组配置对比，把效果分别归因到两项改动；
6. **回到真实任务**跑一遍，并如实清点这套验证还有哪些不可信的地方。

写作纪律：所有数字注明测量来源——"日志实测"、"离线出题测试"、"评分器打分"、"逐轮重算"——不同来源的数字不混用。

## 2. 第一步：看日志——agent 实际怎么查文档

从 7 个任务的运行日志里提取全部文档查询记录。优化组共 109 次调用：45 次关键词查询（search_docs）＋ 64 次点名读取章节（read_section）。

| 任务 | 查询次数 | 点名读取次数 |
|---|---|---|
| calculator | 7 | 6 |
| entry-threshold-task | 3 | 7 |
| flashcard-quiz | 6 | 6 |
| meituan-prototype | 12 | 22 |
| menu-interaction | 7 | 4 |
| rider-plan-hub | 4 | 6 |
| shopping-cart | 6 | 13 |

**发现一：agent 全部用英文 API 名查文档，一条中文都没有。** 45 条查询全部形如：

```
"Grid GridItem layout columns rows"
"padding margin border EdgeMargin EdgePadding object literal syntax"
```

虽然任务说明、文档正文都是中文，agent 查文档时用的却是组件和 API 的英文名。这一点很关键：线上环境没有向量检索（代理服务器只有对话模型，没有 embedding 模型），检索完全靠关键词匹配（BM25），而"英文 API 名关键词"恰好是关键词匹配最擅长的形式。**所以测试题库必须用同样的形式出题**（见第四步），否则测出来的成绩不代表真实使用。

**发现二：查询频率不高。** 每个任务查 3~12 次，优化空间在"每次返回多少"，不在"查多少次"。

**原版 MCP 的日志实测（作为对比基准）**：34 次查询，单次返回量中位数 14200 字符，最大 34800——经常整篇教程全文拖回来。

## 3. 第二步：原版 MCP 差在哪

两个结构性问题：

1. **整本文档挤在一个地址下**。金字塔文档被索引成一个 3MB 的单页，1732 个片段共用一个地址。关键词命中后，系统按"命中段落＋前后相邻段落"拼一大块返回，没法只取想要的那一节。
2. **只有全文一档，没有摘要**。agent 只需要"这个组件有哪些参数"，却被迫收下整篇教程。

离线出题复核：原版对真实查询的召回只有 28.1%——不但贵，还查不准。

## 4. 第三步：两项改动

| 改动 | 内容 | 治什么 |
|---|---|---|
| 改动一：文档拆分 | 把金字塔拆成 265 个独立检索单元（1 篇总索引 ＋ 10 篇案例教程 ＋ 254 篇 API 明细），每篇有独立地址，开头附元信息（层级、主题、API 名清单） | 查不到 |
| 改动二：摘要卡片＋分层读取 | 查询默认只返回每篇的"摘要卡片"（章节目录＋函数签名清单，几百字符）；agent 看中哪篇，再用 read_section 点名读取那一节或全文 | 返回太多 |

工作方式（与金字塔三层结构一一对应）：

```
关键词查询 ──► 摘要卡片（每篇几百字符：列章节和函数名）
               │ 大多数情况看卡片就能写代码
               ▼ 需要细节时点名要
read_section ──► 指定章节全文（1~3K 字符）
               ▼ 需要整篇时
read_section ──► 整篇文档
```

设计原则一句话：**agent 上下文里的每个字符都是它点名要的，没有顺带塞进来的。**

## 5. 第四步：出题——114 道检索测试题

每道题 ＝ 一条查询 ＋ 标准答案（应该返回哪篇文档的哪个章节）。

- **32 道手写题**：刻意模仿第一步日志里看到的真实查询形式（英文 API 名关键词），如 `"Grid GridItem layout grid columns rows"`；
- **82 道自动生成题**：从文档元信息里把 API 名拼成查询。这类题自带答案关键词、偏简单，统计时和手写题分开算，**以手写题的数字为准**；
- **8 道中文题**：防备将来 agent 改用中文提问的底线覆盖。

判分规则（新旧版本都适用）：返回结果的地址包含标准答案的文件路径，或内容包含答案章节的标题／标记，算命中。

指标两个：**召回率**（查得准不准）和**单次返回字符数**（查得贵不贵）。

如实说明一处条件不对等：旧版测试时每次返回 3 条结果，新版定稿是 5 条。但新版返回条数更多反而便宜十倍，这个偏差对结论有利。

## 6. 第五步：对照实验（五组）

| 组 | 配置 | 包含哪些改动 | 召回率（总） | 召回率（手写题） | 单次返回中位字符 |
|---|---|---|---|---|---|
| 1 | 原版 MCP | 无 | 63.2% | 28.1% | 6758 |
| 2 | 只做文档拆分 | 改动一 | 93.9% | 78.1% | 5429 |
| 3 | 拆分，正式库（含另外 4 个文档库同场竞争） | 改动一 | 91.2% | 68.8% | 5420 |
| 4 | 拆分＋卡片，每次返回 3 条 | 改动一＋二 | 89.5% | 62.5% | 405 |
| 5 | **拆分＋卡片，每次返回 5 条（定稿）** | 改动一＋二 | **94.7%** | **81.3%** | **672** |

怎么读这张表：

- **召回率的提升来自文档拆分**：第 1→2 组只做了拆分，真实查询召回就从 28.1% 升到 78.1%；
- **返回量的下降来自摘要卡片**：第 2→5 组只差"卡片"这一项，返回量从 5429 降到 672 字符；
- **卡片会让召回略降**（第 4 组手写题 62.5%），因为摘要比全文难匹配；把每次返回从 3 条提到 5 条、并让同一篇文档只占一个名额后，召回回到 81.3%——这就是定稿"卡片＋返回 5 条"的原因。

注意：672 是离线命令行测出的（只算卡片文本本身）；线上实际返回量见下一步的对照。

## 7. 第六步：放回真实任务验证

条件：7 个界面开发任务（ui-interaction），Android 模拟器，新版执行规则（界面测试一次全过就冻结、编译错误攒一批再修），judge 自动评分，每个任务跑一次。

### 7.1 检索工具在线上的实际表现（日志实测）

| 指标 | 原版 MCP | 改进版 | 变化 |
|---|---|---|---|
| 单次查询返回量（中位） | 14200 字符 | 3404 | **-76%** |
| 单次查询返回量（最坏） | 34800 | 4784 | 最坏情况也被压住了 |
| 单次点名读取（中位） | （无此功能） | 1118 | — |
| 七个任务的检索总注入 | — | 约 42 万字符 ≈ 12 万 token | 占总消耗 4616 万 token 的 **0.26%** |

### 7.2 为什么线上是 3404，不是离线测的 672？

差额来自三个可指认的原因，不是功能失效：① 每张卡片外面还包着编号、文档路径、以及"如何读取全文"的提示语，这些附加文本离线没算；② 几乎每条查询都会命中"总索引"这一篇，它的摘要卡片是一张约 700 字符的目录，偏胖；③ 离线只测卡片文本，线上测的是完整返回内容。另有一个已记录待修的小毛病：总索引的摘要里混进了索引系统的元信息头（界面上显示成 undefined 字样），不影响功能。

### 7.3 端到端成绩

| 维度 | 改进版 | 原版 | 目标 | 达成 |
|---|---|---|---|---|
| judge 平均分 | 83.9 | 84.4 | ≥82.4 | 达标（差 0.5 在单次运行的噪声范围内） |
| token 总量均值 | 659 万 | 410 万 | ≤287 万 / ≤205 万 | **未达标** |

任务层面：7 个任务里 4 个的 token 比原版降了 35%~52%；**美团原型任务是反例，不降反升 81%**——它来回修改了 528 轮（是计算器任务的 3.5 倍），问题出在"改的轮数太多"，检索优化管不到那里。这正是"轮数才是主变量"的直接证据。

## 8. 这套验证还有哪些不可信之处（如实清点）

1. **查询语言依赖当前模型的行为**：45/45 英文关键词查询是 GLM-5.2 现在的用法；换一个爱用中文提问的模型，关键词匹配对中文分词的表现没有测过（题库里只有 8 道中文题兜底）；
2. **离线测试没有 agent 参与**：只测工具本身，测不出"agent 会不会用好它"；
3. **端到端每个任务只跑了一次**：0.5 分的差距不做数（同任务重跑波动 ±28%）；
4. **新旧版返回条数不齐**（3 条 vs 5 条），已在第五步声明；
5. **token 统计口径有过教训**：系统自带的统计在会话接续场景会漏记（最多漏 8 倍），本文所有 token 数字都是从运行日志逐轮重算的；
6. **评分器有抖动**：同一份产物两次评分能差 40 分，所以只看 7 个任务的平均分，不看单任务。

## 9. 结论

1. **工具层面（可信度高）**：两项改动各自有效、可分开验证——文档拆分把真实查询召回从 28.1% 提到 81.3%，摘要卡片把线上单次返回量降 76%，且最坏情况被压在 4784 字符（对 agent 的上下文预算来说，"最坏不超过多少"比"平均多少"更重要）；
2. **使用层面（可信度中）**：agent 正常接受并使用新工具，"查摘要→点名读全文"的用法成立（45 次查询跟进 64 次点名读取）；
3. **端到端层面（否定结论）**：检索返回量只占总消耗 0.26%，优化检索省不动总 token；要省总账，管住"来回轮数"（执行规则）比优化检索有效得多；
4. **方法层面**：这套六步流程（看日志→找问题→做改动→出题→对照实验→回到真实任务＋清点局限）可以直接搬到任何"自有文档＋检索工具"的优化上。

## 10. 如何复现

```bash
cd /Users/user/Desktop/project/docs-mcp-server

# ① 生成拆分后的文档语料（265 个检索单元，带元信息和摘要块）
python3 docs-cjmp/build_corpus.py

# ② 建索引库（5 个文档库，金字塔部分 1304 个片段）
node dist/index.js scrape docs-cjmp/corpus-scrape.yaml

# ③ 离线出题测试（定稿组；改 --store / --limit / --detail 可复现第五步其余各组）
python3 docs-cjmp/eval/run_eval.py --store <索引库路径> --detail cards --limit 5 --out docs-cjmp/eval/rerun.jsonl

# ④ 从任务运行日志提取查询记录（对任意 bench 任务工程）
python3 - <<'EOF'
import json, glob
for f in glob.glob('<任务>/workspace/<工程>/bench-run/opencode.stdout.jsonl'):
    for line in open(f):
        if '"cjmp-docs_' not in line: continue
        ev = json.loads(line)
        if ev.get('type') == 'tool_use':
            p = ev['part']; print(p['tool'], p['state']['input'], len(p['state'].get('output','')))
EOF
```
